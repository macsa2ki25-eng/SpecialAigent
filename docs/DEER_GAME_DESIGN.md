## 1. 画面：縦2段

指がゲーム画面にかからないので、キャラが指で隠れる問題が根本的に消える。
v0.3 までの「指のオフセット」設定は不要になったので削除した。

```
┌──────────────┐
│              │  上段：ゲーム画面（canvas 224×176）。横幅いっぱいに広げる
│   ゲーム画面   │  参道は x 8〜216（208px = 13タイル）
│              │  プレイヤーは y 20〜160
├──────────────┤
│ スコア／倍率  │  下段：DOM
│ きょり／汚れ  │  スコア・ベスト・ばいりつ・きょり・グレイズ・よごれ
│              │
│  操作パッド   │  なぞった位置がそのまま目標位置（絶対指定）
│              │  ワープはしない。移動速度は 150px/s で頭打ち
└──────────────┘
```

パッドには指の位置（輪）とキャラの実際の位置（点）を両方出す。
そのずれが「追いついている途中」の手応えになる。

**ゲーム画面は横幅いっぱいに広げる。**左右に余白を作らない。
そのため整数倍ではなく端数倍で拡大するが、スマホは devicePixelRatio が2〜3あるので
実機ではピクセルのムラは見えない。縦は画面高の46%で頭打ち（下段を潰さないため）。

### 横画面を見送った理由

v0.3 で横画面（288×160）を推したが、縦2段のほうが良い。
横は前方視界が短くて「急に現れる」感じは出るが、**速度の上限が5.16タイル/sに縛られる**。
縦2段なら視界11.1タイルを確保しつつ、指はゲーム画面に触らない。両取りできる。

| | 縦2段（採用） | 横画面（v0.3案） |
|---|---:|---:|
| ゲーム画面 | 224×176 | 288×160 |
| 前方視界 | 11.13タイル | 9.38タイル |
| 速度上限 | 6.12 t/s | 5.16 t/s |
| 指が画面にかかる | **かからない** | かかる |

## 2. 鹿のフンは丸いコロコロ

1粒 4×4px。実物どおり、落ち方に3種類ある。

| 種類 | 重み | 中身 |
|---|---:|---|
| ばらけ | 0.45 | 2〜4粒を幅30pxに散らす |
| **かたまり** | 0.42 | **8〜12粒**を 13×9px の楕円内に落とす |
| でかいの | 0.13 | 7×7px を1つ。当たり判定は広いが、かすめた見返りも大きい |

置く量は「1行(16px)あたりの塊の数」で決める。
行は毎秒 v 行流れてくるので、**実際の湧き量は v × これ**。
速度が上がるだけで密度も勝手に上がるため、係数自体は緩やかにしか増やさない。

```
poopRate(D) = (0.8 + 0.5·(1 − e^(−D/500))) × (参道幅 / 128)
            = 1.30 → 2.11 塊/行     ※ 参道が208pxに広がったぶんを補正
```

**道の途中で立ち止まってフンをする鹿**もいる（距離200mから、鹿の18%）。
画面の少し奥で止まり、1.5秒かけて7粒落としてから歩き去る。
落ちた粒は**回廊の中にも積もる**——見えているところで起きるので公平で、
しかも後述の「回廊が見えてしまう」問題を自然に崩してくれる。

## 3. グレイズ：フンのすぐそばを通ると伸びる

当たり判定の外側 **8px** に入っただけで「かすめた」。1粒につき1回だけ。

```
ゲージ += 0.20（小粒）／ 0.50（でかいの）     上限 2.0
ゲージ *= e^(−0.7·dt)                        指数で減衰
倍率 = 1 + ゲージ                            ×1.0 〜 ×3.0
かすめ点 = 30（小粒）／120（でかいの）× 倍率
被弾すると ゲージ × 0.5
```

**減衰を指数（ゲージ比例）にしているのが肝。**
定数で引くと「稼ぎ続けるか、ゼロか」の二択になって倍率が死ぬ。
実装当初は定数で引いていて、実測したら59秒間ずっと ×1.00 のままだった。

指数なら釣り合い点が

```
ゲージ = 毎秒のグレイズ数 × GAIN ÷ DECAY
```

になり、どの腕前でも意味のある値に落ち着く。目安：毎秒1回で ×1.29、毎秒3回で ×1.86。

被弾でゲージを全没収するのも同じ理由でダメだった（倍率が一生育たない）。半分残す。

## 5. 難易度カーブ

上限は**画面の縦幅から逆算する**。反応時間の下限を固定して割り戻すのが順序。

```
D = 進んだ距離 [m]   ※ 1m = 1タイル = 16px

── まず画面から上限を決める ───────────────
前方視界 FIELD = (プレイヤー安全帯のy − 鹿の出現y) / 16 = 11.13 タイル
反応時間の下限 T_min = 1.2 [s]                （設計値・動かさない）
接近速度の上限 = FIELD / T_min = 9.27
  v_max = 0.66 × 9.27 = 6.12      u_max = 0.34 × 9.27 = 3.15

── そのうえでカーブを引く ─────────────────
スクロール速度  v(D) = 2.8 + (6.12 − 2.8)·(1 − e^(−D/450))
鹿の接近速度    u(D) = min(3.15, 0.9 + 0.7·ln(1 + D/200))
フン密度        ρ(D) = 0.8 + 0.5·(1 − e^(−D/500))       [塊/行]
鹿の出現間隔    I(D) = max(0.55, 3.2·e^(−D/800))
追い鹿の割合    h(D) = min(0.45, D/2500)
牡鹿の割合      c(D) = min(0.20, (D−400)/4000)          ※ D > 400 から
```

| 距離 | 速度 | 鹿速度 | 反応時間 | 塊/行 | 鹿間隔 |
|---:|---:|---:|---:|---:|---:|
| 0 m | 2.80 | 0.90 | 3.01s | 0.80 | 3.20s |
| 100 m | 3.46 | 1.18 | 2.39s | 0.89 | 2.82s |
| 250 m | 4.21 | 1.47 | 1.96s | 1.00 | 2.34s |
| 500 m | 5.03 | 1.78 | 1.64s | 1.12 | 1.71s |
| 1000 m | 5.76 | 2.15 | 1.41s | 1.23 | 0.92s |
| ∞ | 6.12 | 3.15 | **1.20s** | 1.30 | 0.55s |

## 6. 理不尽にしない仕組み（実装で2回壊れた）

配置してから検査するのではなく、**先に通れる回廊を引いてから、その外側にだけ置く**。
——という方針は v0.2 から変えていないが、実装したら2箇所で破れた。
自動テスト（回廊をなぞるボット）で発見して直した。

### 破れ その1：ずれ幅に理論上限をそのまま使っていた

回廊が1行でずれてよい理論上限は `LATERAL / v`。
プレイヤーが**全速力で横に走ってようやく追いつける**量。
毎行その上限を使うと余裕がゼロになり、追いかけるだけで手一杯になって避ける操作ができない。

```
corridorDrift(D) = DRIFT_SAFETY × LATERAL / v(D)      DRIFT_SAFETY = 0.35
```

### 破れ その2：粒が「別の行」に落ちていた

粒は見た目のために行の基準yから上下にずらして置く。
ところが**ずれているあいだにも回廊は横に動いている**ので、
そのままだと「1行ぶん古い回廊」の位置に粒が乗って道が塞がる。

```
必要な空き = CORRIDOR_HALF + 粒の半幅 + |dy| / 16 × corridorDrift(D)
```

### 破れ その3（見た目の問題）：塊が欠けてスカスカに見えた

「適当に置いて回廊に当たったら捨てる」だと塊がごっそり欠ける。
回廊の左右に残っている帯から先に中心を選ぶようにした（`freeCentre`）。

### 破れ その4：回廊が見えていた

**いちばん厄介だった問題。** 回廊にフンを置かないので、そこだけ綺麗な帯になり、
「正解の道」が絵で丸見えになっていた。避けて歩く遊びが、なぞるだけの作業になる。

3つ重ねて消した。

1. **小石を撒く** — 当たり判定の無い灰色の小石を、**6割は回廊の中**に置く。
   フンが入れない場所こそ埋めないと帯は消えない。灰色なので近づけば茶色いフンと確実に見分けられ、公平さは損なわれない
2. **回廊の幅を揺らす** — 半幅を 11〜19px の範囲で行ごとに変える。縁が一定だと帯として読めてしまう
3. **鹿が回廊にフンを落とす** — 上記の「立ち止まる鹿」。決まった安全地帯という前提そのものを崩す

### そのほかの保証

- **予兆**：鹿が画面に入る0.5秒前に、入ってくる辺で印が点滅＋鼻息。牡鹿はさらに0.8秒のため
- **反応時間の下限 1.2秒**。これを固定して速度上限を逆算する
- **無敵時間**：被弾後0.5秒（フン）／1.1秒（鹿）
- **判定は小さめ**：プレイヤーは足元8×6pxのみ
- **逃げ場を作らない**：参道の外へは出られない（縁に植え込みを描いて壁だと分かるように）

### 自動テストの結果

Playwright で3種類のボットを走らせて検証している。

| ボット | 動き | 結果 | グレイズ/m | 平均倍率 |
|---|---|---|---:|---:|
| corridor | 回廊の中心をなぞる | 40秒**生存・フン被弾0** | 0.15 | ×1.15 |
| graze | 回廊の縁を舐める | 96mで死亡 | **0.75** | ×1.40 |
| blind | 何も見ずに振る | 29mで死亡 | 0.55 | ×1.66 |

**安全に歩けば無傷だが稼げない。フンを舐めれば5倍稼げるが死ぬ。** 狙いどおりの分かれ方。

ステージモードでも同じボットで検証している（ステージ1を汚れ0でクリア）。

## 8. モードとランキング

### ふたつのモード

| | 中身 |
|---|---|
| **ステージ** | 100面。ゴール距離まで歩けばクリア。★で評価され、進むと次が開く |
| **エンドレス** | 距離もフンの量も速度も上がり続ける。端末内ランキングに残る |

難易度の式は**両モードで共通**。ステージ n は「エンドレスの距離 (n−1)×18 m 地点から始める」
と読み替えるだけなので、調整箇所が二重にならない。

```
ステージ n の難易度 = (n − 1) × 18 [m相当]
ステージ n の長さ   = 40 + (n − 1) [m]      1面40m → 100面139m
```

### アンロック

- 各エリアの1面は最初から開いている。2面以降は前の面をクリアすると開く
- **次のエリアは、前のエリアで★15個**（30個中）たまると開く。全部★3を取る必要はない
- ★は 汚れ0 で★★★、1〜2 で★★、3〜4 で★

### ランキング（端末内）

エンドレスの上位10件を localStorage に保存する。**サーバーは使わない**。
スコア・距離・かすめた数を記録し、タイトルとリザルトに出す。
自己ベストと今回の順位が分かればじゅうぶんで、
オンライン化はストア公開後に Game Center を足すほうが早い。

## 9. ステージ100の作り方

10エリア × 10ステージ。**チャンク（8〜16行の型）の組み合わせ**で生成する。
型を70個ほど手で作れば100ステージぶんの地形が出る。

| ステージ | エリア | 内容 |
|---|---|---|
| 1–10 | 参道 | チュートリアル。フンのみ → 鹿1頭 |
| 11–20 | 大門 | 柱で通路が狭まる。柱の陰から鹿 |
| 21–30 | 鏡の池 | 水たまり。滑って止まれない |
| 31–40 | 大仏さまの前 | 観光客の群れ。人の流れを読む |
| 41–50 | 若草の坂 | スクロールが速い |
| 51–60 | 石段 | 横移動が段単位に制限される |
| 61–70 | 春日の杜 | 木漏れ日以外が暗い |
| 71–80 | 鹿寄せ広場 | 鹿が大量 |
| 81–90 | 雨の参道 | 水たまり多数。フンと見分けがつかない |
| 91–100 | 夜の奈良 | 暗闇。鹿の目だけが光る |

- 距離は 40m（エリア1）→ 140m（エリア10）
- 各エリアの**10番目はボス**
- 評価は**★3段階**：汚れ0で★★★、1〜2で★★、3〜4で★
- 次エリアの解放は**★15個以上**
- 難易度はエンドレスと**同じ式**を使い、ステージ番号を距離に読み替える

## 10. 技術構成

- **TypeScript + Canvas 2D + Vite**。`image-rendering: pixelated`、横幅いっぱいに拡大
- 更新は固定タイムステップ1/60秒。描画はrAF
- **素材ファイルはゼロ**。ドット絵は文字列、背景は生成、音は矩形波とノイズの実行時合成
- ビルド出力は index.html + js のみ（**gzip 約10KB**）。完全オフライン
- 保存は localStorage
- **Capacitor** でラップ。`base: "./"` のまま `dist/` を同梱
- 縦画面固定・iPhone先行。レーティング4+
- 実在名は避けて架空の古都に
